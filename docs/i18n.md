# i18n

Habitus ships English and Korean. The user picks a language in `/settings` and the choice persists across reload, devices, and sign-out.

## Resolution order

1. `habitus_locale` cookie — read in [src/app/layout.tsx](../src/app/layout.tsx) and passed to `<LocaleProvider initialLocale=...>`. Set client-side by `LanguageToggle` and server-side by `updateLocale` action + auth callback
2. Signed-in user's `user_profiles.locale` column — mirrored into the cookie on sign-in callback
3. Default `"en"`

The cookie is non-httpOnly (so the client provider can rewrite it without a roundtrip) and lives for 1 year.

## Where translations live

- [src/lib/i18n/dictionaries.ts](../src/lib/i18n/dictionaries.ts) — flat key-value dicts for `en` and `ko`. The `en` dict is the master: TypeScript enforces that `ko` has every key
- Add a new key: write it in `en` first, then `ko`. TS will fail the build if `ko` is missing it

## Using translations

In any client component:

```tsx
"use client";
import { useLocale } from "@/lib/i18n/locale-provider";

export function Greeting() {
  const { t } = useLocale();
  return <h1>{t("landing.hero.title")}</h1>;
}
```

For bilingual data (mostly mock data with structured English + optional Korean):

```ts
const region = { en: "Seoul", ko: "서울" };
const label = pick(region); // returns "Seoul" or "서울" based on current locale
```

`pick()` accepts either a plain value or a `{ en, ko? }` object. If `ko` is missing it falls back to `en`.

## Server components

Server components cannot call `useLocale()`. Two options:

1. Render the user-visible H1 / copy from a client child component (preferred for one section)
2. Read the cookie directly with `cookies().get(LOCALE_COOKIE)?.value` and pick the right string from `dictionaries[locale]`

The settings page uses option 1 — the page is a server component but `SettingsClient` renders the H1.

## Adding a new locale

1. Add the literal to the `Locale` union in [src/lib/i18n/dictionaries.ts](../src/lib/i18n/dictionaries.ts) and [src/lib/db/types.ts](../src/lib/db/types.ts)
2. Add a check constraint update to a new migration (e.g. `alter table user_profiles drop constraint ... add check (locale in ('en','ko','ja'))`)
3. Fill out the dictionary
4. Add the locale to the `OPTIONS` list in [src/components/settings/language-toggle.tsx](../src/components/settings/language-toggle.tsx)

## Toggling at runtime

`LanguageToggle` calls `setLocale(next)` from the provider, which:

1. Updates local React state immediately (instant UI swap for client-rendered strings)
2. Writes the cookie via `document.cookie`
3. Calls the server action `updateLocale(next)` which mirrors to `user_profiles.locale` and revalidates the layout
4. Calls `router.refresh()` so server-rendered strings re-render with the new locale

Without step 4 you'd see English in any SSR section and Korean in any CSR section.
